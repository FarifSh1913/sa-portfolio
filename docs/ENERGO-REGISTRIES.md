# Энерго: реестры CRM и ЖКХ

Доработана существующая страница, без второй реализации и без изменения
остальных разделов. Верхний ЛК, sidebar, бело-оранжевая палитра и сетка сохранены.

## Интерфейс

- Источники называются только «CRM» и «ЖКХ», в том числе в legend и modal.
- Два независимых реестра со счетчиками записей. CRM: ФИО, Client ID, счет,
  сокращенный адрес и статус. ЖКХ: счет, ФИО, период, начисления, статус оплаты;
  положительная переплата отмечается отдельным badge.
- Строки — доступные кнопки с hover, focus, chevron и aria-haspopup="dialog".
  Нет технических заголовков «Запись 1» и общего рекурсивного вывода всех полей.
- Детали открываются в одном нативном `<dialog>` поверх страницы: белая карточка,
  затемнение, группировка реквизитов, отдельные финансовые показатели.
  Закрытие по X, кнопке, Esc и клику вне карточки; фон недоступен для фокуса,
  после закрытия фокус возвращается на строку. На небольшом экране окно прокручивается.
- Отдельные состояния обоих реестров: skeleton, success, «Записи не найдены»,
  ошибка с коротким сообщением и «Повторить». HTTP-коды/stack trace в UI не выводятся.
- Русское форматирование денег и дат; PAID/DEBT/PARTIALLY_PAID переведены,
  ACTIVE показан как «Активен». Неизвестный статус отображается нейтрально.

## Фактические HTTP-вызовы

Проверено на preprod 05.10.2026 и через локальный собранный backend:

| Integra endpoint | Метод и тело | Фактический ответ |
| --- | --- | --- |
| `/rest/accaunt-details/all` | GET, без тела | 200, массив из 3 клиентов |
| `/rest/fin-results` | GET, без тела | 200, массив из 3 финансовых записей |
| `/rest/accaunt-info` | POST application/json, requestId/clientId/personalAccount | 200, вложенная агрегированная сводка; обнаружено неверное сопоставление второго счета |

Реестры совпадают с предоставленным контрактом. Записи:

| Client ID | Счет | Клиент | Начисления | Долг | Переплата | Статус |
| --- | --- | --- | --- | --- | --- | --- |
| CL-100245 | 123456789 | Иванов Иван Иванович | 4 150,20 ₽ | 3 250,40 ₽ | 0 ₽ | DEBT |
| CL-100246 | 123456790 | Петров Петр Сергеевич | 2 870,50 ₽ | 0 ₽ | 450 ₽ | PAID |
| CL-100247 | 123456791 | Сидорова Анна Викторовна | 5 210,00 ₽ | 7 210,00 ₽ | 0 ₽ | DEBT |

Во всех CRM-записях accountStatus=ACTIVE, адрес — строка. В финансах период
2026-09, последний платеж передается плоскими lastPaymentAmount/lastPaymentDate.
В ЛК сохранились вложенные personalAccount.lastPayment и client.address.
Это различие явно учтено в отображении, поля не переименованы по догадке.

## Что вызывало ошибку

В предыдущей локальной реализации метод ЖКХ определялся необязательной настройкой
INTEGRA_FINANCE_METHOD. При пустой настройке вызова Integra не было вообще:
ContractUnavailableException превращался в **503**, а не 500. При настройке POST
код мог отправить неподходящий метод, но подтвердить, что именно это вызвало
ранее наблюдавшуюся 500, по текущим данным нельзя. Сейчас реальный GET отвечает 200.

Удалены выбор GET/POST, настройка finance-method, переменная Docker Compose и
обработчик ContractUnavailableException. Оба реестра всегда используют GET без тела.
Пустые null / {} / [] (а также пустое HTTP-тело) нормализуются backend в [].
Неожиданный непустой объект или некорректные элементы массива дают безопасную
ошибку только соответствующей области. JSON десериализует существующий RestClient.
Дополнительные Java DTO для прозрачной передачи реестров не нужны; модели
CrmAccount/FinanceResult описаны в JSDoc и проверяются перед построением UI.

## Ограничение агрегированной сводки Integra

Сопоставление остается в Integra; локального mock или альтернативного объединения нет.
На запрос CL-100246 / 123456790 Integra возвращает root clientId=CL-100246,
но вложенные client.clientId=CL-100245 и personalAccount.number=123456789,
то есть финансовую карточку Иванова вместо Петрова.

Добавлена backend-проверка номера счета и вложенного Client ID. Несовпадение
возвращает безопасный код ACCOUNT_MISMATCH без чужих реквизитов. ЛК показывает
сообщение «Не удалось подтвердить данные выбранного лицевого счета» и retry.

Дополнительно: для Иванова CRM содержит ул. Академика Семенова, а агрегированный
ответ — ул. Ленина. Данные не подменяются на стороне портфолио. Нужно исправить
сопоставление и согласованность источников в Integra. После исправления тот же
POST-запрос будет работать без переключения режима приложения.

независимость ошибок, соответствие счета, исходный evening-plans и маршруты.

обоих источников; X, Esc, фон, кнопка закрытия, восстановление фокуса;
desktop/tablet/mobile (1440, 800, 390, 320px), отсутствие горизонтального переполнения.

retry, null/{}/[], некорректный массив, скрытие технических ошибок и evening-plans.
Новых production mock нет. JavaScript-исключений не обнаружено.

Для воспроизведения запустить приложение на 8098 и Chrome с
`--remote-debugging-port=9235`, затем:

```sh
node src/test/browser/energo-registry.mjs
```

При недоступном CDN можно передать BOOTSTRAP_CSS с путем к точному Bootstrap 5.3.8;
CSS будет подставлен только в тестовом Chrome. SCREENSHOT_DIR задает каталог снимков.
APP_URL и CHROME_URL позволяют переопределить адреса. Часть проверки намеренно
проверяет текущее неверное сопоставление второго счета в upstream: после исправления
Integra этот сценарий следует заменить проверкой успешной сводки Петрова.

После деплоя проверить доступность Integra из контейнера, реальный Bootstrap CDN
и корректность сводки после исправления агрегации на стороне Integra.
